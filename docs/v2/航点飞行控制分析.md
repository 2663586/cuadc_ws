# 航点飞行控制方案分析

> 调研 QGC/PX4 如何实现航点飞行，以及当前 offboard 速度控制为什么不稳定。

---

## 一、PX4 级联控制器架构

PX4 多旋翼控制是三级联结构：

```
Position Setpoint
    ↓
[Position Controller]  ← P 控制器，误差→速度指令
    ↓  velocity setpoint
[Velocity Controller]  ← PID 控制器
    ↓  thrust/attitude setpoint
[Attitude Controller]  ← 姿态角速度控制
    ↓
Mixer → Motors
```

- **Position Controller** 运行在导航频率（EKF 融合率，50–250 Hz）
- 输入：setpoint 位置 vs EKF 估计位置（融合 IMU + 气压计 + GPS）
- 输出：速度指令

- **Velocity Controller** 运行在 IMU 频率（几百 Hz）
- 输入：速度指令 vs EKF 估计速度
- 输出：推力向量 + 姿态指令

关键：这两层控制器**都运行在飞控内部**，直接访问原始传感器数据，延迟是微秒级的。

## 二、`set_velocity_ned` vs `set_position_ned`

| | `set_velocity_ned` | `set_position_ned` |
|---|---|---|
| 进入层级 | 直接进入 Velocity Controller | 进入 Position Controller |
| 被绕过的层 | **Position Controller 整层** | 无 |
| 位置反馈 | ❌ 无 | ✅ EKF 位置估计 |
| 高度保持 | 弱（无位置环积分） | 强（Z 轴 P+积分） |
| 需要外部做什么 | **必须手动实现位置和高度闭环** | 只需告诉目标位置 |
| 适用场景 | 动态避障、视觉伺服 | 航点飞行、定点悬停 |

**后果**：用 `set_velocity_ned` 时，我们 Python 侧（20Hz + gRPC 延迟）必须替代 PX4 的 Position Controller（200Hz+ + 直接传感器访问）。这在物理上不可能稳定。

QGC 和 PX4 Mission 模式从不使用速度控制做航点飞行——它们发送位置 setpoint，让飞控内部处理一切。

参考：
- https://docs.px4.io/main/en/flight_modes/offboard
- https://discuss.px4.io/t/a-few-questions-about-velocity-setpoint/29796

## 三、PX4 Mission 模式 vs Offboard 模式

PX4 的 Mission 模式（QGC 上传航线后使用）额外提供了：

1. **Jerk-limited trajectory generator**：S 曲线速度剖面，加速度也平滑变化
2. **Acceptance radius + turn radius**：接近航点时自动减速、平滑转弯
3. **`position_setpoint_triplet`**：previous/current/next 三个航点，用于前瞻轨迹
4. **TECS**（固定翼）：协调油门/俯仰控制高度和速度

关键参数：

| 参数 | 作用 |
|------|------|
| `MPC_XY_CRUISE` | Auto 模式巡航速度 |
| `MPC_XY_VEL_MAX` | 最大水平速度（offboard 也适用） |
| `MPC_ACC_HOR` | Auto 模式最大水平加速度（offboard 也适用） |
| `MPC_JERK_AUTO` | Auto 模式最大 jerk（S 曲线平滑度） |
| `MPC_XY_P` | 位置环 P 增益（默认 1.0） |

Offboard 模式下，jerk-limited trajectory generator **不激活**。但加速度限制 (`MPC_ACC_HOR`) 仍然生效。这意味着 offboard 位置 setpoint 的阶跃响应是梯形速度剖面（线性加速→匀速→线性减速），而非 Mission 模式的 S 曲线剖面。

## 四、当前问题总结

速度控制（set_velocity_ned）的根本缺陷：

1. **绕过了 PX4 Position Controller** → 丧失了飞控内部的高频位置反馈和积分修正
2. **高度需要手动补偿** → 20Hz Python 循环用 gRPC 查询高度再发送 vz，延迟 50–100ms，控制回路带宽远低于 PX4 内部
3. **前飞倾角导致掉高** → 需要额外的前馈/积分来补偿，而 PX4 的 Position Controller 自动处理
4. **无法利用 PX4 的加速度限制** → 速度指令直接注入 Velocity Controller，没有经过 Position Controller 的平滑

## 五、修复方案：增量位置斜坡

**核心思想**：不再命令速度，改为每周期将位置 setpoint 向目标推进一小步。PX4 的 Position Controller 负责实际的飞行控制。

```
每周期：
  ramp 向目标推进 step = speed / FSM_LOOP_HZ 米
  发送 update_setpoint(ramp) → PX4 内部处理一切
```

为什么稳定：

- **位置反馈在飞控内部**：PX4 比较 setpoint 与 EKF 位置，在几百 Hz 的速率下生成速度指令
- **高度自动保持**：Z 轴 setpoint = 目标高度，PX4 自动控制垂直速度
- **加速度自动受限**：`MPC_ACC_HOR` 限制水平加速度，无需我们干预
- **Python 侧只做"策划"**：每 50ms 更新一次目标位置，飞控做"执行"

稳态行为：
- 斜坡以 speed 匀速前进
- 无人机滞后斜坡约 `speed / MPC_XY_P` 米（纯 P 控制器固有滞后）
- 斜坡到达目标后停止 → 无人机以剩余误差驱动 → 自然减速到达

## 六、后续演进方向

当前使用 offboard 位置斜坡，适合**航点数少、需要 FSM 灵活切换**的场景。

如果后续需要**长距离多航点序列**（如 SearchState 矩形航线），可以考虑：

1. **Offboard 位置斜坡 + 速度前馈**（`set_position_velocity_ned`）：消除 P 控制器稳态滞后，速度方向在拐角直接切换。心跳已支持此模式。

2. **PX4 Mission 模式**：上传 MissionItem 列表到飞控，由 PX4 的 Navigator 全权管理航线执行。FSM 退化为高层监控器。代价：无法在航点中间抢占（需等飞控到达航点后才能切换模式）。

两种方案在 `docs/v2/增量斜坡方案.md` 中有详细对比。
