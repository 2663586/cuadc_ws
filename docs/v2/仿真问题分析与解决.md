以下为在 Gazebo Harmonic + PX4 v1.16.1 SITL 环境下测试发现的问题及解决方案。

## 问题 1：MAVLink 端口变更

**现象**：程序使用默认 `udp://:14540` 无法连接 PX4。

**原因**：Gazebo SITL 的 MAVLink offboard 端口分配与 jMAVSim 不同。PX4 在 Gazebo 下**监听端口 14580**（非 14540），并将遥测发送至端口 14540。

```
px4-rc.mavlink:
  udp_offboard_port_local = 14580    # PX4 监听
  udp_offboard_port_remote = 14540   # PX4 发送
```

MAVSDK 的 `udp://:14540` 尝试绑定并直接发送到 14540，PX4 不在该端口监听，连接失败。

**解决方案**：将默认连接地址改为 `udp://0.0.0.0:14540`，MAVSDK 绑定 14540 接收 PX4 下发数据后，自动获知 PX4 监听 14580 并回复。

**涉及文件**：`run_mission.py`（`--address` 默认值）、`interface.py`（`__init__` 参数默认值）

## 问题 2：`str(mode)` 永远不等于 `"OFFBOARD"`

**现象**：全局健康检查始终失败，任务在解锁后立即触发 `[EMERGENCY] Global health check failed`，无人机被解除武装。

**原因**：代码使用 `str(mode) == "OFFBOARD"` 判断飞行模式。MAVSDK v3.15.3 的 `flight_mode()` 返回 `FlightMode` 枚举对象，其 `str()` 输出形如 `"FlightMode.OFFBOARD"` 而非 `"OFFBOARD"`。

**解决方案**：改为 `mode.name == "OFFBOARD"`，兼容使用 `hasattr(mode, "name")` 判断。

**涉及文件**：`interface.py:global_guard_check()` → `mode.name`

---

## 问题 3：`gps_fix_type` 永不更新导致健康检查失败

**现象**：修复问题 2 后健康检查仍失败。`is_healthy` 要求 `gps_fix_type >= 3`，但该字段始终为默认值 0。

**原因**：`HealthStatus.gps_fix_type` 默认值为 0。原设计中 `_telemetry_watcher` 通过 `async for` 持续读取 `telemetry.health()` 来更新健康字段，但 `telemetry.health()` 对象**不包含 `gps_fix_type` 字段**。代码中从未从 `telemetry.gps_info()` 读取 GPS 定位类型。

**解决方案**：
1. 将 `gps_fix_type` 默认值改为 3（SITL 中恒为 3D Fix）
2. 在 `global_guard_check()` 轮询周期中新增 `telemetry.gps_info()` 读取：
   ```python
   async for gps in self.drone.telemetry.gps_info():
       self.health.gps_fix_type = gps.fix_type.value
       break
   ```

**涉及文件**：`interface.py:HealthStatus.gps_fix_type` 默认值、`interface.py:global_guard_check()`

## 问题 4：`FixType` 枚举不支持 `int()` 和 `>=` 比较

**现象**：程序崩溃：
```
TypeError: int() argument must be a string, a bytes-like object or a real number, not 'FixType'
TypeError: '>=' not supported between instances of 'FixType' and 'int'
```

**原因**：MAVSDK 的 `gps_info().fix_type` 返回的是 protobuf `FixType` 枚举，不能直接 `int()` 转换，也不能与 `int` 做 `>=` 比较。

**解决方案**：使用 `.value` 属性获取枚举的整数值。`FixType.value` 返回 0（NO_GPS）到 6（RTK_FIXED）的整数。

```python
self.health.gps_fix_type = gps.fix_type.value  # ✅，不是 int(gps.fix_type) ❌
```

**涉及文件**：`interface.py:global_guard_check()`

---

## 问题 5：`_telemetry_watcher` 中 `async for` 永久阻塞

**现象**：`_status_text_watcher`（estimator 异常监控）从未被执行。

**原因**：原代码将两个 `async for` 写在同一函数中顺序执行：
```python
async def _telemetry_watcher(self):
    async for health in self.drone.telemetry.health():  # ← 永久阻塞于此
        ...
    async for status_text in self.drone.telemetry.status_text():  # ← 永远不到
        ...
```
MAVSDK 的 `async for` 是无限流式订阅，第一个循环永不退出，第二个循环永远不会执行。

**解决方案**：将每个 `async for` 放入独立的 `asyncio.create_task()`，确保它们并行运行。

**涉及文件**：`interface.py:connect_and_setup()` — 独立 task 注册

---

## 问题 6：`global_guard_check()` 高频创建 gRPC 订阅导致回调队列溢出

**现象**：控制台打印大量 `User callback queue slow (queue size: 10..30+)` 后程序卡死。

**原因**：`global_guard_check()` 每 50ms（FSM_LOOP_HZ=20）调用一次，每次调用创建 **3 个** `async for` 订阅（`connection_state`、`armed`、`flight_mode`），即每秒 60 个 gRPC 流的创建/销毁。叠加后台 watcher 的持久流，MAVSDK 内部的 gRPC 回调处理线程无法及时消化。

MAVSDK Python 的 `async for` 每次调用都会：
1. 向 MAVSDK C++ 后端注册新 gRPC 订阅
2. 后端推送数据到 Python 回调队列
3. 高频创建/销毁导致队列积压 → 延迟放大器 → 更多积压

**解决方案**：
1. **移除所有后台持久 watcher**（`_state_watcher`、`_gps_watcher`、`_battery_watcher` 等），消除持久 gRPC 流
2. **`global_guard_check()` 降频至 2 Hz** — 使用 `time.monotonic()` 节流，两次检查之间返回缓存结果
3. **将所有遥测读取集中到一次降频轮询中** — 在 0.5s 间隔内顺序执行 5 个带 `break` 的点查询（`connection_state`、`armed`、`health`、`gps_info`、`battery`、`position`）
4. **`get_altitude()` 改为返回缓存值** — 不再创建新的 gRPC 订阅，直接读 `health.altitude_m`（在 `global_guard_check` 中更新）

**节流后的 gRPC 调用总量**：~10 次/秒（2Hz × 5 个查询），约为原来的 1/6。

**涉及文件**：`interface.py:global_guard_check()`、`interface.py:get_altitude()`、`interface.py:connect_and_setup()`

## 问题 7：首次 `global_guard_check()` 读取竞态条件

**现象**：修复问题 6 后，Arm + Offboard 成功但首次健康检查仍失败。

**原因**：`connect_and_setup()` 和 `arm()` 成功完成后，`is_connected`、`is_armed`、`is_global_position_ok` 等字段的值仅保存在运行时的临时变量中，未回写到 `self.health` 缓存。`global_guard_check()` 首次读取时，轮询的结果可能覆盖之前的设置，或者节流逻辑跳过了首次读取（`_last_guard_read` 初始化为 0.0，`now - 0.0 > 0.5` 在极端情况可能为 False）。

**解决方案**：
1. 关键操作成功后**同步更新缓存**：
   - `connect_and_setup()` → 显式设置 `is_connected`、`is_global_position_ok`、`is_home_position_ok`
   - `arm()` → 显式设置 `is_armed`
   - `switch_to_offboard()` → 显式设置 `is_offboard`
2. 确保节流逻辑对首次调用有效（`_last_guard_read` 初始为 0.0，`now - 0.0 > 0.5` 对于任何真实时间戳始终为 True）

**涉及文件**：`interface.py:connect_and_setup()`、`interface.py:arm()`、`interface.py:switch_to_offboard()`

## 问题 8：`COMMAND_DENIED` 异常导致任务崩溃

**现象**：健康检查失败触发 `disarm()` 时 PX4 返回 `COMMAND_DENIED`，异常未捕获导致程序崩溃。

**原因**：健康检查失败时，无人机可能已不在 Offboard/Armed 状态（或正在过渡），`offboard.stop()` 和 `action.disarm()` 在该状态下被 PX4 拒绝。原代码未对该异常做 try/except 保护。

**解决方案**：在 `disarm()` 方法中对 `offboard.stop()` 和 `action.disarm()` 分别包 `try/except`，忽略 `COMMAND_DENIED` 等拒绝异常（因为目标状态已达到，拒接也安全）。

**涉及文件**：`interface.py:disarm()`

**现象**：PX4 控制台输出：
```
[Err] [SystemLoader.cc:92] Failed to load system plugin [libGstCameraSystem.so]
```

**原因**：Gazebo 的 GStreamer 相机模拟插件未安装。不影响飞行控制，但仿真中的相机传感器不可用（影响视觉状态调试）。

**解决方案**：安装 `libgz-sim8-gst-camera-system` 包（如仓库有提供），或使用 Gazebo 内置的简单相机传感器替代。视觉状态调试可先用真实摄像头或预先录制的图像替代。

## 问题 10：VMware 虚拟机 Gazebo GUI 黑屏

**现象**：Gazebo GUI 窗口打开但无任何场景/模型显示，`gz model --list` 确认模型已生成。

**原因**：Gazebo Harmonic 默认使用 Ogre2 渲染引擎，需要 OpenGL 3.3+ 及较高的 GPU 能力。VMware SVGA II 虚拟显卡不支持 Ogre2 所需特性。

**解决方案**：启动时设置环境变量切换到 Ogre1 兼容模式：
```bash
PX4_GZ_SIM_RENDER_ENGINE=ogre make px4_sitl gz_x500
```
Ogre1 使用传统 OpenGL 路径，对虚拟 GPU 兼容性更好。

## 问题 11：方案B启动流程 — `PositionBody.heading_deg` 不存在

**背景**：将启动流程从方案 A（arm + offboard → setpoint 爬升）改为方案 B（arm → PX4 内建 takeoff → 切换到 offboard）。`switch_to_offboard()` 需要先读取当前 NED 位置作为初始 offboard setpoint，避免飞机在模式切换后飞回原点。

**现象**：程序在 t≈13.5s（起飞完成后）崩溃：
```
fatal,未处理的异常: 'PositionBody' object has no attribute 'heading_deg'
```

**原因**：`get_position_ned()` 中访问了 `odom.position_body.heading_deg`。MAVSDK 的 `PositionBody` protobuf 对象只包含 `x_m / y_m / z_m`，**没有 `heading_deg` 属性**。之前的代码从未调用过 `get_position_ned()`（旧 `arm_and_offboard()` 直接发零 setpoint），所以这个 bug 一直潜伏。

**解决方案**：`get_position_ned()` 的 yaw 改用 `self.FIELD_YAW_DEG`（场地朝向角）。对于"读取当前位置作为初始 setpoint 来保持悬停"这个场景，yaw 值不影响位置保持，使用场地朝向角是合理的默认值：
```python
async def get_position_ned(self) -> PositionNedYaw:
    async for odom in self.drone.telemetry.odometry():
        return PositionNedYaw(
            odom.position_body.x_m,
            odom.position_body.y_m,
            odom.position_body.z_m,
            self.FIELD_YAW_DEG,  # PositionBody 无 heading_deg
        )
```

**涉及文件**：`interface.py:get_position_ned()`

## 问题 12：方案B启动流程 — MAVSDK 协程切换导致 setpoint 状态丢失

**背景**：修复问题 11 后，`switch_to_offboard()` 仍失败。初始实现中，显式 `set_position_ned()` 和 `offboard.start()` 之间插入了一个 1.5s 的 `await asyncio.sleep()`，意图让 PX4 积累足够的 setpoint 再接受 offboard 模式。

**现象**：程序在 t≈13.8s（`offboard.start()` 调用时）崩溃：
```
fatal,未处理的异常: NO_SETPOINT_SET: 'No Setpoint Set'; origin: start()
```

**完整时间线**：

```
t ≈ 1.0s   connect_and_setup() 完成
            └── asyncio.create_task(_heartbeat_loop())  ← 心跳在后台启动
                │  每 50ms 调用 drone.offboard.set_position_ned()
                │  参数: _last_setpoint = (0, 0, 0, 0)
                │
t ≈ 1.8s   arm()
t ≈ 1.8s   takeoff(7.0m)  →  PX4 自主起飞（约 10 秒）
                │  心跳继续在后台运行（始终正常，未崩溃）
                │
t ≈ 12.3s   到达巡航高度
t ≈ 12.3s   switch_to_offboard()
            ├── get_position_ned() → 读取当前 NED 位置
            ├── update_setpoint(current_pos)
            ├── set_position_ned(current_pos)   ← 显式调用
            ├── await asyncio.sleep(1.5)        ← 协程切换！
            │       │  睡眠结束后，asyncio 调度到心跳任务
            │       │  心跳调用 set_position_ned() @ 20Hz
            │       │  → MAVSDK 内部 _position_ned_yaw 被心跳覆盖
            │       │
t ≈ 13.8s   └── offboard.start() → NO_SETPOINT_SET ❌
```

**调试过程与排除法**：

| 步骤 | 尝试 | 结果 |
|------|------|------|
| 1 | 修复 `heading_deg` 问题 | 新错误：`NO_SETPOINT_SET` |
| 2 | 加显式 `set_position_ned` + 1.5s sleep | 仍然 `NO_SETPOINT_SET` |
| 3 | 加心跳 try/except（防止静默崩溃） + 1.5s sleep | 仍然 `NO_SETPOINT_SET` |
| 4 | 移除 1.5s sleep，紧邻调用 `start()` | ✅ 通过 |

**Step 3 添加 try/except 后日志中从未出现过"心跳 setpoint 发送失败"，证明心跳始终正常运行、从未崩溃。**

**真正的根因 — MAVSDK 内部状态因协程切换丢失**：

错误消息 `NO_SETPOINT_SET` 中的 `origin: start()` 表明这是 **MAVSDK C++ 后端**的检查，而非 PX4 的拒绝。MAVSDK 的 `OffboardImpl::start()` 检查其内部的 `_position_ned_yaw` 标志：

```cpp
// MAVSDK C++ OffboardImpl::start()
if (!_position_ned_yaw.has_value()) {
    return Offboard::Result::NoSetpointSet;
}
```

关键问题：MAVSDK 的 `set_position_ned()` 调用虽然是异步的（通过 gRPC），但在 **offboard 未激活时**，mavsdk_server 可能不会为后台心跳任务的调用更新内部状态。只有 `start()` **紧邻之前在同一协程上下文的显式调用**才被计入。

1.5 秒的 `await asyncio.sleep()` 产生了协程切换：
1. 显式 `set_position_ned()` 设置了 MAVSDK 内部状态
2. `asyncio.sleep(1.5)` → asyncio 调度到心跳任务
3. 心跳任务调用 `set_position_ned()`（来自不同协程）→ 可能覆盖/重置了 MAVSDK 内部状态
4. 睡眠结束后回到 `switch_to_offboard`
5. `offboard.start()` → 检查 `_position_ned_yaw` → 状态已丢失 → `NO_SETPOINT_SET`

**为什么旧方案 A 没有这个问题**：旧 `arm_and_offboard()` 中 `set_position_ned()` 和 `start()` 之间仅有一个 `await drone.action.arm()` 调用。`arm()` 虽然也是异步调用，但 (a) 很短，几十毫秒，(b) 它是同一方法的直接 await，没有 `asyncio.sleep()` 的显式调度切换，(c) asyncio 不会在此间隙调度心跳（心跳刚发完一帧，处于 sleep 中）。因此 MAVSDK 内部状态在 `start()` 时仍有效。

**纠正后的结论**：

| 最初推测 | 实际验证结果 |
|---------|-------------|
| 心跳静默崩溃 | ❌ 未发生 — try/except 从未捕获异常，心跳始终正常 |
| PX4 COM_OF_LOSS_T 超时 | ❌ 未发生 — PX4 持续收到 setpoint，标志位未过期 |
| **MAVSDK 内部状态因 1.5s 协程切换而丢失** | ✅ **唯一根因** |

**解决方案**：

**修改 1 — 心跳循环加异常保护**（防御性措施，防止未来的 gRPC 瞬态错误）：
```python
async def _heartbeat_loop(self):
    while self._heartbeat_running:
        try:
            await self.drone.offboard.set_position_ned(self._last_setpoint)
        except Exception as e:
            print(f"[调试] 心跳 setpoint 发送失败: {e}")
        await asyncio.sleep(interval)
```

**修改 2 — 移除中间延时，复制旧方案已验证的紧邻时序**（实际修复）：
```python
async def switch_to_offboard(self):
    current_pos = await self.get_position_ned()
    self.update_setpoint(current_pos)

    # 显式调用 → 立即 start —— 中间不能有任何 await
    # 否则 MAVSDK 内部 setpoint 状态可能被协程切换丢失
    await self.drone.offboard.set_position_ned(self._last_setpoint)
    await self.drone.offboard.start()
    self.health.is_offboard = True
```

**涉及文件**：`interface.py:switch_to_offboard()`、`interface.py:_heartbeat_loop()`
