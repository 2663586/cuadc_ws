# CUADC 2026 多旋翼无人机侦察与救援 — 比赛方案

## 一、赛事核心要求总结

> 以下内容基于《2026CUADC竞赛规则（非正式版）》整理。

### 1.1 任务背景

多旋翼无人机侦察与救援项目以应急救援和危险品侦察任务为背景，聚焦侦察救援无人机高精度、高效率、自动化的运行需求，主要考察多旋翼无人机的**自主飞行控制系统设计**、**目标识别**、**精准空投**、**快速部署**等方面的综合能力。

任务要求：携带 2 瓶 550ml 标准载荷 → 全自主起飞 → 投放至指定圆筒 → 侦察危险品标识 → 返航精准着陆。以投放和侦察准确、任务用时短取胜。

### 1.2 飞行器技术要求

| 项目 | 要求 |
|------|------|
| 动力 | 仅限电动机为动力的多旋翼飞行器 |
| 电压 | 电池组最高输出电压 ≤ 26V（6S），电池数量不限，必须为市售成品且表面标明参数 |
| 轴距 | 对角线方向旋翼轴间距 ≤ 550mm |
| 数量 | 每个机组比赛中只能使用一架飞行器 |
| 操控 | 启动后全程自主，**不允许任何形式的人工操纵** |
| 安全 | 必须配备螺旋桨防护罩 + 可由人工切断动力的安全开关 |
| 载荷 | 必须能挂载 2 瓶市售带标签未开封的 550ml 饮用水（自备） |
| 挂载 | 挂载方式自行设计，投放前标准载荷视为飞行器一部分 |
| 能力 | 飞行中自动投放标准载荷 + 对地面设施自动侦察 |
| 干扰 | 两组同时比赛，飞行器干扰问题由参赛机组自行解决 |

### 1.3 场地设置

比赛场地由三个子区域组成：

**起降区（33m × 8m）**
- 起降点：直径 80cm 圆形区域，中间有 "H" 标识
- 起降点圆心距离准备区 3m
- 起降点前 2m 处设置起飞线
- 准备区位于起降区边线外侧

**投放区（8m × 5m）**
- 位于起降点前方 30m 处
- 放置 3 个高 30cm 的白色圆筒，随机排列：
  - 1 号筒：直径 **15cm**（最高分 500 分）
  - 2 号筒：直径 **20cm**（300 分）
  - 3 号筒：直径 **25cm**（100 分）
- 有效区分为：
  - **A 区**：圆筒内部区域（投中计满分）
  - **B 区**：以筒心为圆心、直径 1m 的圆环区域（投中计 50 分）
  - **无效区**：投放区中除 A、B 区以外的区域
- A 区和 B 区地面颜色为**蓝色**，无效区以实际场地为准

**侦察区（8m × 5m）**
- 位于投放区前方 20m，距起降点 55m
- 放置 5 个高 15cm、直径 20cm 的白色圆筒，随机排列
- 其中 **3 个筒内随机放置 12×12cm 危险化学品标识**各 1 个

> 各区域规定尺寸可能存在误差，以现场实际情况为准。

### 1.4 比赛流程

1. **赛前审核**：抽签顺序将飞行器摆放到审核区，关闭所有电子设备（计算机可睡眠）
2. **进场准备**（1 分钟）：接到口令后进入准备区 → 打开电源 → 演示安全开关 → 飞行前检查 → 举手示意 "准备完毕"
3. **比赛**（5 分钟）：
   - 将飞行器放至起降点 → 安装标准载荷 → 按下计时器启动开关 → 开启飞行器
   - 全自主起飞 → 投放区 → 投放 2 瓶水 → 侦察区 → 识别标识 → 返航着陆
   - 机组通过图传信息填写成绩记录单 → 停表
4. **回收**：飞行器完全静止后方可回收

**关键约束**：
- 两个标准载荷均投至投放区，且至少一个投至有效区，才可继续侦察任务
- 着陆和填写成绩记录单无顺序要求
- 比赛时间开始后，除紧急停止外不允许任何人工操纵

### 1.5 成绩评定

单轮成绩 = 起飞分 + 空投分 + 侦察分 + 着陆分 + 时间分：

**起飞分**（50 分）：携带两个标准载荷飞越起飞线即为成功，否则 0 分。

**空投分**：以标准载荷第一落点判定

| 落点             | 得分       |
| -------------- | -------- |
| 1 号筒 A 区（15cm） | 500      |
| 2 号筒 A 区（20cm） | 300      |
| 3 号筒 A 区（25cm） | 100      |
| B 区（筒外圆环）      | 50       |
| 无效区或投放区外       | 0（且比赛终止） |

> 注意：两个载荷投中同一个 A 区只计一次；投至同一个 B 区计两次；有载荷投至投放区外或两个均投无效区则**比赛终止**。

**侦察分**：100 × 正确数 - 100 × 错误数 + 0 × 空白数
- 每正确填写一个圆筒内的危险品标识 → +100 分
- 错误填写 → -100 分，不填 → 0 分

**着陆分**（50 分）：在比赛时间内无损着陆在起降点内（所有对角线旋翼轴连线交叉点投影在起降点圆内，压线算入内），螺旋桨停止旋转。

**时间分**：200 × (300 - T_task) / 300
- T_task 为计时器记录的时间（秒），尾数舍去
- 时间分精确到 1 分，四舍五入，最小为 0
- **只有完赛才能获得时间分**，否则为 0

完赛条件：起飞 + 空投（空投分不为 0）+ 侦察（至少一个正确）+ 着陆成功 + 填写成绩单

**最终成绩**：两轮中取较高一轮成绩。如成绩相同，以另一轮成绩排序。

### 1.6 终止比赛与判罚

**终止比赛**（已取得成绩有效）：
- 飞行器触地
- 未完成投放即携带载荷进入侦察区
- 载荷投至投放区外或两个均投无效区
- 停表时未填写成绩记录单
- 飞行器在比赛时间内未着陆
- 停表时螺旋桨未停止
- 开启飞行器后有任何人工操纵

**该轮零分**：
- 螺旋桨旋转前未按下计时器
- 起飞未成功或未飞越起飞线即着陆
- 起飞未挂载标准载荷
- 比赛结束飞行器未着陆且未停表
- 零件脱落、解体或坠毁
- 飞入安全区两次（首次警告）
- 未经裁判允许提前打开电源或有明显安全隐患

**取消比赛资格**：
- 赛前审核不合格且更换后仍未通过
- 起飞前提前确定投放/侦察区圆筒位置
- 飞行器触碰人员
- 未经允许打开图传
- 发现作弊行为（取消本届资格）

## 二、整体任务流程

```
起飞 → 投放区巡航(30m) → 视觉识别圆筒 → 精准投放2瓶水 → 侦察区(55m)
→ 扫描5个圆筒 → 识别3个危险品标识 → 返航 → 精准着陆(80cm圆)
```

## 三、硬件方案

### 3.1 飞行平台
- **机架**：550mm 轴距四旋翼机架（如 TBS Source One 或定制碳纤机架）
- **电机**：2216/2810 级别无刷电机，KV 值 900-1100
- **电调**：40A BLHeli_32 电调 ×4
- **桨**：10-11 寸螺旋桨 + 防护罩
- **电池**：6S 锂聚合物电池（容量 4000-6000mAh，满足 5 分钟 + 冗余）
- **飞控**：Pixhawk 6C / CUAV X7+ 运行 PX4 固件
- **机载计算机**：Raspberry Pi 5 (8GB) 或 NVIDIA Jetson Orin Nano
- **摄像头**：
  - 下视摄像头（用于投放瞄准与精准着陆）：800W 像素 USB/CSI 摄像头
  - 前视/下视两用：广角摄像头用于侦察区圆筒扫描
- **图传**：5.8G 模拟图传或数字图传（仅用于人工观察，不用于飞控）
- **投放机构**：舵机驱动的挂载释放机构（双通道，可分别投放两瓶水）
- **安全开关**：外置物理开关，可人工切断总电源

### 3.2 地面站
- 笔记本电脑运行 QGroundControl（仅用于监控，不介入飞行）
- 数传电台（3DR/Holybro 915MHz）
- 计时器（由裁判统一启动，机组自备备用）

## 四、软件架构

### 4.1 概述
#### 技术栈
- 使用运行在机载电脑上的MAVSDK（Python，[v3.15.3](https://github.com/mavlink/MAVSDK-Python/releases/tag/3.15.3)）程序直接和PX4（[v1.16.1](https://github.com/PX4/PX4-Autopilot/tree/v1.16.1)）飞控通信，控制无人机的行为。关于MAVSDK，可见[[MAVSDK简介]]
- 机载电脑处理来自摄像头（推荐：USB 接口 800W/1080P 广角摄像头，如 ELP-USB8MP02G-L75 或 Waveshare IMX219-120，需通过 `cv2.VideoCapture()` 直接读取）的图像。
- 飞控控制电调、舵机（推荐：E-Max ES08MA II 金属齿轮模拟舵机 或 GDW DS290MG 数字舵机，通过飞控 AUX 输出 + `set_actuator` 指令控制）

### 4.2 状态机任务流程

程序结构强调分模块，通过状态模块的组合来组成不同任务。以下是仿真测试用test_queue

```python
self.mission_queue = [
    # 起飞已由 PX4 内建 takeoff 在 FSM 启动前完成
    HoverState(hover_time=1.0),             # 短暂稳定

    TransitState(north=30.0, east=0.0, up=7.0, speed=5.0),  # 飞往投放区上空
    HoverState(hover_time=1.0),
    DropState(bottle_index=1),              # 下降至5m→识别1号筒→悬停对准→投放第1瓶
    DropState(bottle_index=2),              # 识别2号筒→投放第2瓶

    TransitState(north=55.0, east=0.0, up=7.0, speed=5.0),  # 飞往侦察区上空
    ReconState(),                           # 下降至3m扫描→识别5个筒→分类危险品标识→记录结果
    HoverState(hover_time=1.0),

    TransitState(north=0.0, east=0.0, up=5.0, speed=5.0),   # 返航
    PrecisionLandState(),                   # 基于视觉的精准着陆
]
```

比赛流程不同主要在于视觉部分的参与。

### 4.3 比赛流程说明

#### 起飞

1. `takeoff(target_alt=7.0)` ：起飞至安全高度（7m）。
2. `HoverState(hover_time=1.0)`：等待稳定

注意事项：
- 确认无人机处于 Offboard 和 Armed 模式下才可以开始发送起飞指令。

#### 投放

1. `TransitState(north=30.0, east=0.0, up=7.0, speed=5.0)`：传输目标位置与飞行速度；飞行到投放区起点。
2. `HoverState(hover_time=1.0)`：等待稳定。
3. `DropState(bottle_index=1) && DropState(bottle_index=2)`：发送指令控制舵机投放水瓶。

> 详见 [[圆筒检测与投放]] — 已整理完成两级检测 + 视觉伺服对准方案。

#### 侦查

1. `TransitState(north=55.0, east=0.0, up=7.0, speed=5.0)`：飞到侦查区起点
2. `ReconState()`：只需要设置一个在侦查区域内的矩形航线就可以了，保证将场地内的标识通过图传传到地面站就行。

#### 降落

1. `TransitState(north=0.0, east=0.0, up=5.0, speed=5.0)`：飞回原点（或者可以飞到Home点？）
2. `PrecisionLandState()`：使用两种方案：①1. 飞行至起降区上空后下视摄像头搜索地面 "H" 标识，视觉伺服对准 80cm 直径圆形区域，缓慢下降至 0.5m 后切换 AUTO.LAND 模式，确保着陆后所有轴心投影在起降点内；②将视觉作为兜底方案，直接让飞机飞回0,0,0点，在高度比较低的情况下进入“着陆保险”状态，下降率降低，根据视觉部分获得的降落区域标识坐标再改变下降率直至着陆。这两种方案需要看实际飞机飞行的时候返航精度如何。

## 五、关键技术挑战及解决方案

### 5.1 投放精度
- **挑战**：需要将水瓶投入直径仅 15cm 的圆筒（1 号筒最高分）
- **方案**：
  - 多级视觉对准：GPS粗定位（~1m）→ 视觉检测圆筒 → 悬停对准 → 投放
  - 水瓶下落轨迹建模（考虑风力）
  - 投放高度控制在圆筒上方 1.5-2m（减少下落偏移）

### 5.2 侦察识别精度
- **挑战**：从飞行高度（2-3m）准确识别 12×12cm 小标识
- **方案**：
  - 高分辨率摄像头（≥ 1080P）
  - 侦察阶段降低飞行高度至 1.5-2m
  - 每个圆筒悬停 3-5 秒多次拍摄
  - 训练数据增强（模糊、噪声、光照变化）

### 5.3 时间优化
- **挑战**：5 分钟内完成起飞+投放+侦察+着陆全程
- **方案**：
  - 巡航速度提升至 5-8 m/s
  - 投放区侦察并行化（到达后立刻开始视觉处理，不等悬停稳定）
  - 时间预算：起飞 20s + 投放区 90s + 侦察区 90s + 返航着陆 60s

### 5.4 抗干扰
- **挑战**：两组同时比赛，RF 干扰
- **方案**：
  - 数传使用不同频段
  - 视觉导航为主，GPS 为辅（GPS 仅用于航线规划，视觉用于精准定位）
  - 冗余通信链路

### 5.5 安全机制
- 实时监控电池电压，低于阈值自动返航
- 遥控器保持连接，安全员可随时切回 STABILIZED 模式
- 现有代码中的看门狗（Watchdog）机制已实现 OFFBOARD 丢失检测
